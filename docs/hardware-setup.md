## 1. 项目目标与当前系统架构

当前系统的目标是让 L80-R GPS 模块持续输出 NMEA 数据，由 ESP32 解析真实 WGS84 经纬度和 GPS UTC 时间，在获得新的有效定位后通过主 Wi-Fi 网络向 FastAPI 的 /location 接口发送 HTTP POST，并由后端写入数据库。同时，ESP32 自己建立 GPS_MONITOR 本地 Wi-Fi，供手机在没有 USB 串口监视器的情况下直接查看 GPS、UART、Wi-Fi 和上传状态。

| 链路 | 数据路径 | 用途 |
|---|---|---|
| 定位上传链路 | L80-R → ESP32 → YOUR_WIFI_SSID → FastAPI → 数据库 | 正常业务功能：自动上传新的有效 GPS 定位 |
| 手机诊断链路 | L80-R → ESP32 → GPS_MONITOR → 手机浏览器 192.168.4.1 | 现场调试：不需要 Arduino 串口监视器即可看状态 |

> **两个 Wi-Fi 功能相互独立** ESP32 使用 WIFI_AP_STA 模式：STA 端连接主热点 YOUR_WIFI_SSID 负责 FastAPI 上传；AP 端建立 GPS_MONITOR 负责手机本地诊断。没有手机连接 GPS_MONITOR 时，数据库上传仍可自动进行。反过来，即使主热点或 FastAPI 不可用，只要 ESP32 正常运行，手机仍可连接 GPS_MONITOR 查看本地状态。

## 2. 本次对话中已经验证有效的排障路径

本次问题不是通过一次修改直接定位，而是逐步将 GPS、UART、供电、Wi-Fi、HTTP 和数据库拆开测试。以下步骤是实际有效、以后可以重复使用的排障路径。

最初现象：完整固件曾在电脑 USB 供电和合适位置得到实际经纬度，但改用充电宝后出现不能定位或看不到数据的现象。初期存在“充电宝电源噪声、GPS 搜星、供电稳定性、程序阻塞”等多个可能性。

先拆掉 Wi-Fi 与 HTTP：使用最小 GPS UART 测试程序，只运行 HardwareSerial + TinyGPSPlus，直接打印 NMEA 和 charsProcessed()，把 FastAPI、数据库和网络变量全部排除。

通过 NMEA 证明串口链路：当接线正确时出现 $PMTK、$GPGGA、$GPGLL、$GPGSA、$GPGSV、$GPRMC、$GPVTG 等数据，且 gps.charsProcessed() 从 0 持续增长，证明 GPS CPU、UART 波特率和 ESP32 接收链路都在工作。

A/B 确认 GPS 小板的实际数据针脚：断电换线后测试得到：GPS 小板丝印“TX”接 ESP32 接收脚时字符数为 0；GPS 小板丝印“RX”接 ESP32 接收脚时持续出现 NMEA。因此在这块实际成品小板上，丝印“RX”的针脚应按 GPS_DATA_OUT 使用。

确认 charsProcessed() 的含义：将有效数据线换走后，字符数停在某个累计值不再变化。该数值不会自动归零，因此“5476、5476、5476……”表示没有新的 UART 字符进入，而不是 GPS 仍在正常工作。

发现物理接触故障：进一步扰动测试发现有一根杜邦线在面包板上的接口不紧。该虚接可以造成数据流随机中断，也可以让“电脑供电正常、移动后充电宝异常”看起来像电源差异，实际却是移动设备改变了接触状态。

恢复完整上传固件：在确认数据针脚和连接可靠后，将完整 GPS + Wi-Fi + FastAPI 固件恢复，并将 ESP32 GPS_RX 固定为 GPIO14、GPS_TX 为 GPIO13。

增加本地手机诊断：为解决“充电宝供电时没有 USB 串口可看”的问题，在完整上传固件上增加 WebServer 和 GPS_MONITOR AP，使手机连接 192.168.4.1 即可实时判断 UART、搜星、Fix、ESP32 运行和 HTTP 上传状态。

> **当前最重要的结论** 此前异常中至少有一项已经被实际确认：杜邦线 / 面包板接触不可靠会直接使 GPS UART 数据流停止。因此，在连接可靠性没有确认前，不能仅凭“电脑 USB 可用、充电宝不可用”就判定充电宝存在电源或射频问题。

## 3. 已确认的硬件与 UART 接线结论

| GPS 小板端 | ESP32 端 | 当前结论 |
|---|---|---|
| RX（小板丝印） | GPIO14 | 已通过实际 NMEA A/B 测试确认：本项目中作为 GPS 数据输出接入 ESP32 RX |
| TX（小板丝印） | GPIO13 | 当前代码定义为 GPS_TX；如果 ESP32 不需要向 GPS 发送命令，物理上可暂不接 |
| VCC | 3.3V | 使用 ESP32 3.3V 供电 |
| GND | GND | 必须可靠共地 |

固件中的 UART 定义固定为：

```
#define GPS_RX 14
#define GPS_TX 13
```

> **不要再按普通 RX/TX 字面重新推断** Quectel 原始模块的 UART 通常遵循 TXD 为输出、RXD 为输入，但本项目使用的是实际成品小板，已经通过 NMEA 实验确认“小板丝印 RX → ESP32 GPIO14”能够持续输出数据。以后分析这套硬件时应优先采用这一实测事实，避免再次因为丝印含义造成反复换线。

## 4. NMEA、搜星、定位与 UART 状态的判断方法

GPS“没有定位”和“完全没有串口数据”是两类不同故障。当前增强版固件正是通过 lastGpsByteTime、charsProcessed()、satellites 和 location 状态把两者分开。

| 观察结果 | 实际含义 | 主要检查方向 |
|---|---|---|
| GPS累计字符 = 0，或很快停止增长 | ESP32 没有持续收到 GPS UART 字符 | 数据线、GPIO14、VCC、GND、面包板、GPS 是否启动 |
| GPS字符持续增长，有 $GPGGA/$GPRMC 等，但卫星数 0、位置无效 | GPS 模块和 UART 正常，当前只是未搜到星/未形成 Fix | 室外视野、天线朝向、建筑遮挡，之后再评估电源噪声 |
| 卫星数逐步增加但仍无 Fix | GPS 正在搜星和收敛 | 保持开阔天空、等待首次定位 |
| 位置有效，出现经纬度和 GPS UTC | 已经获得有效 Fix | 继续检查 HTTP 状态和数据库 |
| 字符数固定不动，“距最后GPS字符”持续增大 | UART 数据流中断 | 优先查杜邦线/接触/VCC/GND，不要误认为只是“搜不到星” |

本次曾实际看到类似：

```
$GPGGA,235943.021,,,,,0,0,,,M,,M,,*41
$GPGSV,1,1,00*79
$GPRMC,235943.021,V,,,,,0.00,0.00,050180,,,N*48
```

其中 GGA 的 Fix Quality=0、GSV 的可见卫星为 00、RMC 状态 V 都说明“GPS 串口正在工作，但当前定位无效”。在这种状态下，日期/时间字段也不能当成可信卫星时间。因此曾出现的 2080-01-05 不能当作真实 GPS UTC；当前正式固件只有在 location/date/time 都有效时才保存并上传 latestFix。

## 5. 基础版固件的完整功能清单

基础版指此前只包含 GPS + Wi-Fi + FastAPI 上传、主要依靠 Arduino Serial Monitor 调试的固件。它已经具备较完整的业务逻辑，不是简单的“读经纬度并每 5 秒无条件上传”。

- 使用 TinyGPSPlus 解析 L80-R 的 NMEA 数据。
- 使用 ESP32 HardwareSerial(2) 读取 GPS，当前接收脚固定为 GPIO14。
- 只有 gps.location.isUpdated() 时才尝试捕获新的位置，避免反复处理完全相同的缓存位置。
- 同时检查 location、date、time 的有效性；任一无效都不保存本次 Fix。
- 经纬度保持 GPS 原始 WGS84，不在 ESP32 固件中进行高德等坐标系转换。
- 把 GPS 日期和时间格式化为 ISO 8601 UTC，例如 2026-08-30T12:00:00Z。
- 使用 gpsTimeKey 将年月日时分秒组合成可比较的数值，用于判断新的 GPS 时间是否晚于上次成功上传时间。
- 保留 latestFix，并记录 capturedAt，用于判断定位新鲜度。
- 设置 GPS_FIX_MAX_AGE_MS=10000：超过 10 秒的旧 Fix 不上传。
- 每 5 秒只“检查”是否存在新的有效 Fix，不是每 5 秒强制重复写旧坐标。
- 连接主 Wi-Fi；初始连接等待期间仍持续 readGPS()，减少因 Wi-Fi 阻塞导致 NMEA 丢失。
- Wi-Fi 断开后按间隔自动重连，而不是在 loop 中长期阻塞等待。
- 通过 HTTP POST 向 /location 发送 device_id、longitude、latitude、gps_time。
- 只有 HTTP 2xx 才把该 GPS 时间标记为成功上传，服务器失败时不会错误地认为数据已入库。
- 具有基础 GPS 串口健康检查：启动一段时间后如果几乎没有字符，会在串口提示检查 RX/TX、供电和波特率。

> **基础版的主要限制** 拔掉电脑 USB 改成充电宝独立供电后，Arduino Serial Monitor 不再可用。此时即使数据库不再更新，也很难现场判断是 GPS 没搜到星、UART 断流、ESP32 重启、主 Wi-Fi 未连接、FastAPI 不可达还是服务器返回错误。

## 6. 当前增强版固件的完整功能清单

当前增强版保留基础版的全部定位与上传逻辑，并增加 ESP32 本地 AP + WebServer 诊断能力。它既是正式上传固件，也是现场检测固件。

- 完整保留基础版的 GPS 解析、有效性校验、UTC 时间、Fix 新鲜度、去重、Wi-Fi 重连、HTTP POST 和 2xx 成功判定。
- HTTP_TIMEOUT_MS 当前为 2000 ms，服务器不可达时比原先较长超时更快返回，减少阻塞。
- ESP32 使用 WIFI_AP_STA：STA 连接主热点 YOUR_WIFI_SSID，AP 同时建立 GPS_MONITOR。
- 手机连接 GPS_MONITOR 后打开 http://192.168.4.1，即可访问 ESP32 自己提供的诊断网页。
- 手机是否连接 GPS_MONITOR 不影响主 Wi-Fi 自动上传；无人查看网页时设备仍独立运行。
- 每收到一个 GPS UART 字节都会更新 lastGpsByteTime，因此即使楼内没有卫星定位，也能证明 GPS 数据链路是否仍在工作。
- GPS_UART_TIMEOUT_MS=3000：超过 3 秒没有 GPS 字符时，网页提示 UART 无数据 / 数据流可能已断。
- 网页显示 GPS 累计字符 gps.charsProcessed()、有效 NMEA 校验数、校验失败数和距最后一个 GPS 字符的毫秒数。
- 网页显示卫星数、HDOP、纬度、经度、GPS UTC 时间和最近有效 Fix 距今时间。
- 网页显示 ESP32 运行时间，可用于发现设备是否发生过重启。
- 网页显示主 Wi-Fi 是否已连接以及 RSSI。
- 网页显示最近 FastAPI 上传状态、最近 HTTP Code 和最后一次成功上传的 GPS 时间。
- 网页每 2 秒自动刷新，适合充电宝供电、室外移动测试和现场排故。

## 8. 最终硬件连接与烧录前检查

| 连接项 | 推荐连接 |
|---|---|
| GPS 小板 RX（实测 NMEA 数据口） | ESP32 GPIO14 |
| GPS 小板 TX | ESP32 GPIO13；如果当前不发送 GPS 配置命令，也可暂不接 |
| GPS VCC | ESP32 3.3V |
| GPS GND | ESP32 GND |
| ESP32 供电 | 调试时电脑 USB；独立测试时充电宝 USB |

> **烧录前必须做的两项隐私配置** 在附录固件中找到 WIFI_SSID="YOUR_WIFI_SSID" 和 WIFI_PASSWORD="YOUR_WIFI_PASSWORD"，只在本地 Arduino 工程里替换为实际主热点名称和密码。不要把修改后含真实密码的源代码公开分享。

- 确认那根曾经松动的杜邦线已经更换或重新可靠固定。
- 轻微摇动 VCC、GND、GPS RX→GPIO14、USB 插头时，不应再造成 GPS 字符数冻结。
- FastAPI 电脑当前局域网 IP 如果不再是 10.33.22.115，需要只修改 SERVER_URL 中的 IP。
- GPS 陶瓷天线测试定位时应朝向开阔天空；楼内主要测试 UART，不要求获得 Fix。

## 9. Arduino 烧录与首次启动方法

1. Arduino IDE 中安装/确认 TinyGPSPlus 库可用；WiFi.h、HTTPClient.h、WebServer.h 属于 ESP32 Arduino 环境常用组件。
2. 选择与你实际 ESP32 开发板对应的 Board 和正确串口。
3. 复制附录 A 的完整代码到 Arduino 工程。
4. 将 YOUR_WIFI_SSID 和 YOUR_WIFI_PASSWORD 替换为实际主热点凭据。
5. 如果 FastAPI 电脑 IP 已变化，更新 SERVER_URL；其余代码先不要改。
6. 编译并烧录。
7. 调试阶段打开串口监视器，波特率选择 115200。
8. 正常启动时应看到 GPS UART 初始化、GPS_MONITOR 启动、诊断网址、主 Wi-Fi 连接结果等输出。

## 10. 手机 GPS_MONITOR 实时诊断使用方法

| 参数 | 当前固件设置 |
|---|---|
| 诊断 Wi-Fi 名称 | GPS_MONITOR |
| 诊断 Wi-Fi 密码 | 12345678 |
| 诊断页面 | http://192.168.4.1 |
| 页面刷新 | 每 2 秒自动刷新 |

1. 给 ESP32 上电。可以是电脑 USB，也可以是充电宝。
2. 在用于查看状态的手机/平板/电脑上搜索 Wi-Fi，连接 GPS_MONITOR。
3. 如果系统提示“该 Wi-Fi 无互联网连接”，这是正常的；选择保持连接/仍然使用此网络。
4. 打开浏览器，输入 http://192.168.4.1。
5. 先观察“总体状态”和“GPS UART 数据流”，再观察卫星、经纬度、ESP32 状态和 FastAPI 上传状态。

> **重要网络限制** 192.168.4.1 是 ESP32 的本地 AP 地址。设备必须连接 GPS_MONITOR 才能正常访问这个地址。没有连接 GPS_MONITOR 时，不能把 192.168.4.1 当作互联网地址远程访问。

> **如果主热点由同一部手机提供** 很多手机无法在“自己开启主热点”的同时再作为 Wi-Fi 客户端连接 GPS_MONITOR。更稳妥的测试方式是：手机 A 开主热点供 ESP32 和 FastAPI 电脑联网，手机 B / 平板 / 另一台电脑连接 GPS_MONITOR 查看诊断页。只有一部手机时，可以在需要诊断时暂时切换到 GPS_MONITOR；切换期间主热点上传会暂时中断。

## 11. 不同场景的具体测试方法

### 11.1 楼内：只验证设备和 UART 是否稳定

楼内卫星信号很弱，“暂无有效定位、卫星数 0”本身不代表故障。楼内最重要的是确认 UART 连续性。

- GPS UART 显示“正常”。
- GPS累计字符每次刷新都明显增加。
- 距最后GPS字符通常保持在较小的毫秒值，而不是持续增长到数秒。
- ESP32运行时间持续增加，不应突然重新从很小的秒数开始。

### 11.2 室外：验证搜星和真实定位

1. 保持代码和接线不变，把 GPS 天线朝上放在开阔天空处。
2. 观察卫星数是否从 0 逐渐增加。
3. 等待总体状态从“GPS 正在工作，等待定位”变成“GPS 已定位”。
4. 确认页面出现合理的纬度、经度和 GPS UTC。
5. 如果主热点和 FastAPI 可用，再观察上传状态是否出现 HTTP 2xx / 上传成功。

### 11.3 电脑 USB 与充电宝 A/B 对比测试

这个实验必须只改变供电方式，避免再次把“移动接线”和“改变电源”混在一起。

| 步骤 | 条件 | 记录指标 |
|---|---|---|
| A | 电脑 USB 供电，设备位置固定 | 运行时间、GPS字符、距最后字符、卫星数、Fix、HTTP状态 |
| B | 不改接线、不改位置、不改代码，只换充电宝 USB | 记录同样指标 |
| C（必要时） | 充电宝仍供电，但拉开充电宝与 GPS 天线距离 | 若仅 C 明显改善搜星，再考虑电源/射频干扰 |

### 11.4 不连接 GPS_MONITOR 时

不连接 GPS_MONITOR 完全不影响正式上传。只要 ESP32 能连接主热点 YOUR_WIFI_SSID、FastAPI 可达并且 GPS 获得新的有效 Fix，固件会自主向数据库链路发送数据。GPS_MONITOR 是“查看窗口”，不是上传前提。

## 12. FastAPI 与数据库上传验证方法

1. 让 FastAPI 电脑和 ESP32 连接到同一主热点 YOUR_WIFI_SSID。
2. 确认电脑局域网 IPv4；如果不是代码中的 10.33.22.115，修改 SERVER_URL。
3. 启动后端，例如：uvicorn main:app --host 0.0.0.0 --port 8000。
4. 将 GPS 放到可获得有效定位的位置。
5. 诊断页观察“最近上传状态”和“最近 HTTP Code”。
6. HTTP 200 或其他 2xx 表示 ESP32 已经收到服务器成功响应；随后确认数据库 gps_time / 经纬度出现新的记录。

> **主热点不一定需要互联网** 如果 FastAPI 和 ESP32 都在同一个手机热点局域网中，ESP32 访问电脑的 10.x / 192.168.x 私网地址属于局域网通信，热点本身是否能访问公网通常不是必要条件。真正必要的是双方在同一网络、IP 正确、FastAPI 监听 0.0.0.0 且电脑防火墙允许相应端口。

## 13. 各种故障状态的判断与处理

| 现象 | 判断 | 优先操作 |
|---|---|---|
| 网页能开，UART正常，字符持续增长，卫星0 | GPS和UART正常，只是未定位 | 楼内可继续稳定性测试；需要定位时转到室外 |
| 网页能开，字符数固定，距最后字符不断增大 | GPS UART 数据流断 | 检查 GPS小板RX→GPIO14、GND、3.3V、杜邦线、面包板 |
| 网页能开，运行时间突然变小 | ESP32发生重启 | 检查充电宝、USB线、5V输入、电源接触；必要时再查 brownout |
| 网页能开，主 Wi-Fi 显示未连接 | STA 联网失败 | 检查 YOUR_WIFI_SSID / YOUR_WIFI_PASSWORD、热点是否开启、距离和兼容性 |
| GPS已定位，但最近上传状态为 HTTP连接失败 | 定位链路正常，网络/服务器链路异常 | 检查 SERVER_URL、电脑IP、FastAPI进程、防火墙 |
| GPS已定位，服务器返回错误 | HTTP可达但服务器返回非2xx | 查看 FastAPI 日志、接口字段、数据库错误 |
| HTTP 2xx，但数据库没有新记录 | ESP32到FastAPI链路成功，问题更靠后端 | 检查 /location 处理逻辑、事务提交、数据库表和查询条件 |
| GPS_MONITOR 搜不到 | ESP32未启动、AP未成功或距离问题 | 检查供电、ESP32是否重启、靠近设备重新扫描 |
| 连接 GPS_MONITOR 后 192.168.4.1 打不开 | 手机可能切换了移动数据/未保持本地Wi-Fi，或ESP32异常 | 确认仍连接 GPS_MONITOR，关闭“自动切换到移动数据”后再试 |
| 轻碰设备后字符立即冻结 | 高度指向物理接触问题 | 直接更换杜邦线或焊接，不要优先改代码 |

## 14. 硬件可靠性与正式部署建议

- 当前项目已经实际遇到面包板/杜邦线接触不紧，因此正式设备不建议长期依赖松动面包板。关键的 VCC、GND、GPS_DATA_OUT（小板 RX）应改为可靠排针、锁紧连接器或焊接。
- GPS VCC 与 GND 走线尽量短，GPS 数据线避免被 USB 线或外壳机械拉扯。
- 可在 GPS 模块 VCC 附近预留 100nF + 10µF 去耦；如果后续确实观察到供电瞬态，还可以再评估增加几十 µF 的储能电容。
- GPS 天线远离大电流开关电源、充电宝 DC-DC、电感和高频数字线。在确认连接可靠后，如果“电脑供电能搜星、充电宝供电始终卫星0”能够稳定复现，再进行充电宝距离/电源噪声 A/B 实验。
- 测试时一次只改变一个变量：不要同时换供电、移动天线、换杜邦线、改代码，否则无法确认哪项真正产生影响。

## 15. 后续可选固件优化建议（本次不修改代码）

以下项目只是工程优化建议。本次 Word 附录代码严格保持当前成功版本的逻辑，不把这些改动直接合并进去。

增加 ESP32 复位原因：在诊断页显示上电复位、软件复位、看门狗、Brownout 等原因。这样运行时间归零后可以进一步判断供电还是软件复位。

网页总体状态加入 Fix 新鲜度：当前页面会显示“最近有效定位距今”供人工判断。未来可以让顶部“GPS 已定位”同时要求 latestFix 年龄小于阈值，以区分“刚刚有效”与“历史上曾经有效”。

扩大 GPS UART 接收缓冲区：可评估在 GPSSerial.begin() 前设置更大的 RX buffer，例如 1024/2048 字节，以提高网络阻塞时对 NMEA 峰值积压的容忍度。

进一步减少 HTTP 对 GPS 的阻塞：目前超时已经是 2000ms。后续如需要更高鲁棒性，可把网络发送放到独立 FreeRTOS 任务或队列中，让 GPS 读取任务始终高频运行。

诊断热点密码配置化：当前 GPS_MONITOR 密码固定为 12345678，便于调试。正式部署时可改成设备唯一密码或从配置区读取。

主热点凭据独立配置：可使用 Preferences/NVS 或单独 secrets.h 管理主热点和服务器参数，避免每次修改主程序。

服务器地址更稳健：当前 SERVER_URL 使用固定局域网 IPv4。后续可考虑电脑固定 DHCP 地址、静态 IP、mDNS 或在设备侧提供配置页面，减少热点重新分配 IP 后的人工修改。

## 16. 最短操作流程

1. 确认硬件：GPS小板 RX→GPIO14，VCC→3.3V，GND→GND；TX→GPIO13 可接或按当前需要处理。
2. 在附录代码中把 YOUR_WIFI_SSID / YOUR_WIFI_PASSWORD 换成实际主热点凭据。
3. 确认 FastAPI 电脑 IP；必要时改 SERVER_URL。
4. Arduino 编译并烧录。
5. 充电宝供电后，用另一台手机/平板连接 GPS_MONITOR，密码 12345678。
6. 浏览器打开 http://192.168.4.1。
7. 楼内先看：UART正常、GPS累计字符持续增长、运行时间持续增长。
8. 室外再看：卫星数增加、出现“GPS 已定位”、经纬度合理。
9. 保持主热点和 FastAPI 运行，观察 HTTP 2xx / 上传成功。
10. 最后检查数据库是否不断出现新的 gps_time 和坐标记录。
