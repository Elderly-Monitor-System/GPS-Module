# 0. V7.0 决策与状态管理规则

## 0.1 四份材料的严格决策优先级

最新对话已经最终确定的内容 >  技术路线母版与原技术基线 > 当前前后端代码事实核验 > 网页功能规划辅助资料。对话负责回答“最后决定怎么做”，V5.0负责保持文档结构与历史基线，代码负责确认“实际上已经做到什么”，网页规划负责补充交互清单；网页规划与后续对话冲突时，以后续对话为准。

## 0.2 冲突处理原则

出现 A / B / C 三套方案时，不做平均折中；只采用最后一次已经明确确认的 C。被废弃的旧方案仅在故障复盘或版本差异说明中保留，不能作为当前 V7.0 方案并列选项。

## 0.3 待定事项的统一写法

凡对话、V5.0、代码和网页规划均没有形成最终答案的内容，统一使用“【待定】”。每个“【待定】”必须同时写清：① 为什么当前不能确定；② 最推荐方案；③ 推荐实施步骤；④ 验证方式；⑤ 验证通过后如何转为正式决策。

## 0.4 “已实现”与“优化建议”严格分层

当前代码已经存在但用户体验仍存在问题的功能，写成“功能已实现/交互待优化”；尚未实施的方案一律写成“【未实施优化】”，不得因为推荐方案合理就提前写成系统现状。

## 0.5 本版总体状态判断

- 【已实施 / 阶段性验证】当前已形成 L80-R → ESP32 → WiFi 局域网 → HTTP POST /location → FastAPI → MySQL → GET 查询 → JavaScript 2 秒轮询 → 高德地图显示的定位链。真实 GPS 解析与自动上传已接入，但坐标系转换、定位质量、独立供电、断网恢复和长时间运行尚未最终验收；4G/公网、gps_time、鉴权与安全监护扩展仍属于后续阶段。

# 1. 项目核心概述

## 1.1 一句话项目目标

本项目拟开发一套以具备联网能力的老人便携式监护设备为硬件载体，以 GPS 连续定位为第一核心链路，并在 GPS 主链稳定后逐步集成 SOS、跌倒检测、语音对讲、电量监测、摄像头抓拍、设备绑定、多用户鉴权、电子围栏和安全告警等功能的老人户外安全监护系统；监护端通过 Web 页面查看老人当前所在位置、当天轨迹、历史轨迹和设备状态。

## 1.2 v5.0项目第一核心目标（主要目标已实现）

当前阶段不同时开发所有监护功能，从 GPS 从“固定数据能够显示”已经推进到“设备能够自动上传、数据库连续保存、网页自动刷新、当天轨迹默认显示、历史日期和具体时间可查询”的完整数据闭环。GPS 闭环稳定以后，跌倒、电量、摄像头、SOS 等模块复用同一套“设备上传→FastAPI→MySQL→前端读取”的分层框架。

## 1.3 最终 GPS 双向数据链

写入链（设备→数据库）：


### 2.6.7 Marker 颜色、业务语义与重合规则

| 颜色/对象 | 固定语义 | 重合时处理 |
| --- | --- | --- |
| 绿色 Marker | 当天第一条有效 GPS = 起点 | 不因查询位置重合而改变颜色 |
| 蓝色 Marker | 今天最新有效 GPS = 当前所在位置 | 若与起点或查询位置同坐标，保留各自语义并视觉轻微错位 |
| 红色 Marker | 历史日期最后一条有效 GPS = 当天终点 | 若只有1条数据，与橙色起点同坐标但错位显示 |
| 橙色 Marker | 指定时间对应的最近有效 GPS = 查询位置 | 允许与起点/当前/终点同坐标；点击显示实际命中时间 |
| Polyline | 按 gps_time 从早到晚连接当天有效 GPS | 0或1条记录时不强行画无意义线段，格50m取一次点 |

轨迹点本身不全部创建可见 Marker。轨迹由 Polyline 承载；起点、当前点、历史终点和指定时间位置分别承担明确业务语义。点击指定时间 Marker 可查看更详细的查询结果信息。

### 2.6.9 gps_time 与服务器写入时间

- 【已确定 / 已共识】当前 locations 表中的 timestamp 继续表示服务器/数据库写入时间。真实 GPS 阶段优化时新增 gps_time；设备采集时间与服务器写入时间必须分开保存，以处理断网补传、延迟上传、乱序上传，并为历史轨迹排序和指定时刻查询提供真实时间依据。

现有 locations 表只有 timestamp，且该字段当前由 MySQL DEFAULT CURRENT_TIMESTAMP 自动生成，因此它更接近“服务器/数据库写入时间”。正式数据结构将新增 gps_time，并继续保留服务器写入时间，用于日志、延迟分析和排错。

```text
GPS 10:00 采集位置 A
↓（设备断网缓存）
10:10 网络恢复并上传
↓
gps_time = 10:00（老人实际位置时间）
timestamp = 10:10 左右（服务器写入时间）
```

## 2.14 Index、Foreign Key 与 Trigger 的项目定位

Index：用于加速查询。当前 locations 的主键 id 已自动建立 PRIMARY 索引，并已通过 EXPLAIN 验证 ORDER BY id DESC LIMIT 1 使用 PRIMARY 进行 Backward index scan。

Foreign Key：用于不同数据表之间的引用完整性。当前 locations 尚未设置外键；后续 devices/user_devices 等表建立后再按数据模型评估。

Trigger：数据库在 INSERT/UPDATE/DELETE 时自动执行的逻辑。当前不使用 Trigger。项目业务规则优先放在 FastAPI 中，避免关键业务逻辑隐藏在数据库触发器内。

# 5. 已遇到的问题、确认原因与最终解决办法

## 5.1 最新代码与旧版路线的直接冲突

旧版文档中部分交互状态来自计划或对话确认，而不是最新代码事实。V7.0 已在原章节直接纠正：今日轨迹按钮重复点击不会返回实时定位；历史按钮重复点击可以返回；单点仍创建 Polyline；重合 Marker 没有轻微错位；首次初始化失败后不会启动后续轮询。

## 5.2 后端重复函数和重复路由

后端代码材料中 calculate_distance、simplify_track、query_track_range 以及 today/date/range 路由重复出现。Python/FastAPI 可能因注册顺序表现为仍可运行，但重复定义会让后续人员误改未生效版本，也可能使 OpenAPI 文档或调试结论产生歧义。

- 【安全清理方法】先记录全部接口请求与响应样例，建立最小自动测试；确认只保留一套函数和路由；删除重复块；重启服务并核对 /docs；重新执行实时、今日、历史、range、nearest 与异常输入测试。未完成这套回归前，不直接在正在联调的主文件中随意删除。

## 5.3 坐标系偏移问题

L80-R 输出的经纬度属于 GNSS 原始坐标语义，最新固件直接上传，前端直接用于高德地图。当前未见 WGS-84 到 GCJ-02 的转换，因此地图点位可能出现系统性偏移。该偏移不能简单归咎于卫星数或模块精度。

最终策略是数据库保留原始 WGS-84，查询或展示层生成 GCJ-02；字段命名必须带坐标系，防止重复转换。验收时选取开阔场地、建筑入口、道路交叉口等已知点，对比原始值、转换值和高德显示位置。

## 5.4 固件网络恢复不足

当前 connectWiFi() 在 setup 阶段持续阻塞直到连接成功；运行期间 WiFi 掉线只打印“暂不上传”并返回，没有主动重连。HTTPClient 也未设置明确超时，网络异常可能拖慢 loop，进而影响持续读取 NMEA。

推荐把联网、采集、上传拆成非阻塞状态机：GPS 字符读取始终最高频执行；WiFi 按退避间隔重连；HTTP 设置连接和读取超时；失败记录进入有限环形队列；恢复后按 gps_time 补传。

## 5.5 敏感凭据暴露

最新材料中出现 WiFi 密码、MySQL root 密码、高德 Web Key 与 securityJsCode。V7.0 仅保留占位符。项目组应轮换旧凭据、建立最小权限数据库账号、限制地图 Key 域名，并把真实配置排除在版本控制和提交材料之外。

## 5.6 时间与“最新位置”语义

当前 GET /location 按全表 id DESC 取最新插入记录，不按 device_id 过滤；timestamp 是数据库写入时间。单设备、无补传时表面可用，但多设备、延迟上传或乱序补传后，“最后插入”不等于“该设备最后采集”。后续必须按设备和 gps_time 查询。

| 问题/现象 | 确认原因 | 最终解决办法 / 固化结论 |
| --- | --- | --- |
| 地图底图有 POI，但老人位置不明显 | 高德自身 POI 与定位标记容易混淆 | 继续使用 AMap.Marker；用 HTML/CSS content 自定义明显蓝色定位针 |
| 直接运行 main.py 后终端结束 | 只定义 FastAPI app 不等于启动 Web Server | 当前统一使用 python -m uvicorn main:app --reload |
| 5500 前端访问 8000 失败/涉及跨域 | 不同端口属于不同 Origin | FastAPI CORS 显式允许本地5500来源；正式部署再收紧 |
| 直接双击 HTML 与当前通信方式不一致 | file:/// 不是当前标准 HTTP Origin | 前端固定 python -m http.server 5500 |
| Live Server 与 Python http.server 选择 | 两者都可提供静态HTTP，但 Live Server 增加扩展/端口变量 | 当前分阶段验证固定使用 Python http.server |
| Workbench 左侧未立即看到新对象 | 对象树需要刷新 | 以 Action Output 为执行结果依据，必要时 Refresh SCHEMAS |
| 重复 CREATE TABLE 报 Error 1050 | 表第一次已创建成功 | 不删除成功表，只停止重复执行 |
| 重复 INSERT 会多出记录 | INSERT 是真实数据写入 | 每次 INSERT 明确目的并核对 rows affected / id |
| Tables/Functions/Foreign Keys/Triggers 容易理解成“文件夹/硬件功能” | Workbench 显示数据库对象类别 | Tables=表；Functions=存储函数；Foreign Key=表关系；Trigger=数据库事件逻辑 |
| 担心排序百万行会很慢 | 是否慢取决于查询计划与索引 | EXPLAIN 验证 PRIMARY + Backward index scan；后续按查询模式设计索引 |
| ORDER BY id DESC 能否代表真实最新GPS | 模拟阶段 id 与插入顺序一致；真实设备可能延迟/乱序上传 | 真实轨迹统一引入 gps_time；id 保留唯一记录编号 |
| MySQL 程序目录与 Data Directory 混淆 | Server 程序与数据文件不是一回事 | 数据由 MySQL 管理在 D:\MySQL_Data；禁止手工修改数据文件 |
| Workbench 是否必须一直开 | Workbench只是客户端 | 运行链只需要 MySQL Server、FastAPI、前端HTTP Server；Workbench按需打开 |

### 8.4.5 最新 ESP32 固件执行流程

固件使用 TinyGPSPlus、WiFi 和 HTTPClient。GPSSerial=HardwareSerial(2)，RX=13、TX=14、9600 baud。setup() 初始化 GPS 后调用 connectWiFi()；loop() 持续读取串口字符并执行 gps.encode(c)，每当 millis()-lastUpload≥5000 ms 调用 uploadGPS()。

uploadGPS() 先检查 WL_CONNECTED，再检查 gps.location.isValid()；只有两项均成立才读取经纬度、输出卫星数/海拔/UTC 时间，并发送 device_id、longitude、latitude。当前 UTC 时间只输出到串口，没有写入请求体。

- 【字段边界】当前后端只接收 device_id、longitude、latitude，因此固件暂不上传 gps_time。不能把串口打印出的 UTC 时间误写成数据库已保存的 GPS 时间。

### 8.4.6 固件配置脱敏与可复现方式

可复现文档应列出变量名、用途和示例格式，不保存真实值。推荐通过独立 secrets.h/config_private.h 或构建参数提供 WIFI_SSID、WIFI_PASSWORD、SERVER_URL 和 DEVICE_ID，并将私密文件加入忽略清单。

### 8.5.5 指定时间查询：/locations/nearest + ±5分钟

- 【已实施 / 已验证】后端先将查询时间扩展到前后5分钟窗口，再按 ABS(TIMESTAMPDIFF(SECOND, timestamp, target_datetime)) 选择最近记录；成功返回 query_time、gps_time（当前字段实际对应 timestamp）、difference_seconds、longitude、latitude、id。

### 8.5.6 轨迹抽稀算法：50米距离阈值（考虑是否间隔太大，缩小距离阈值）

## 8.6 阶段6：安全监护扩展模块

### 8.6.1 户外场景可靠性：GNSS / 网络 / 设备状态

- 【未实施优化】真实户外场景下不能把“数据库存在坐标”直接等同于“老人此刻仍在该位置”。后续设备端至少需要区分定位有效、无星/暂时无定位、网络不可用、上传失败、设备重启、低电等状态，并由服务端和网页分别承担规则判断与展示。

- 【待定 / 推荐优化】真实设备报文字段尚未最终确定。推荐至少保留 device_id、device_time/gps_time、server_receive_time、message_id、message_type、protocol_version，并在 POST 接口实现重复消息检测；弱网重试时，服务端根据 message_id 或稳定组合键判断是否重复写入。设备鉴权推荐采用独立设备凭证，避免仅凭 device_id 字符串写入。实施后通过重复发送同一报文、乱序发送和协议版本变更进行验证。

### 8.7.3 HTTPS、密钥和配置安全

- 【未实施优化】当前本地验证允许使用开发配置；正式公网环境不得继续硬编码数据库密码、地图密钥或设备密钥。推荐：① 使用环境变量/配置管理；② 生产接口强制 HTTPS/TLS；③ 收紧 CORS；④ 日志中不打印敏感凭据；⑤ 设备凭证可轮换。验证采用密钥缺失、错误密钥、过期凭证和跨 Origin 访问测试。

### 8.7.4 服务端健康、日志、备份与恢复

【未实施优化】监护首页后续应优先回答“老人现在是否安全”，推荐主视图保留地图，同时增加最新位置时间、在线/离线、设备电量、SOS、电子围栏状态和未处理告警摘要；设备配置、账号与高级查询放到次级区域，避免首页被工程调试信息占满。

- 【未实施优化】正式部署还需要处理服务宕机、数据库异常、日志审计、备份与恢复。推荐增加健康检查接口、结构化日志、数据库定期备份和恢复演练，并记录 API 错误率、设备在线率、最后有效定位时间等运维指标。验证至少覆盖 FastAPI 重启、数据库短时不可用、备份恢复和异常日志定位。

- 推荐验证方法：先用 Python 自动模拟器生成确定性测试数据，再逐项注入故障；同时增加真实 ESP32 + L80-R 的实机测试。每项记录输入、预期输出、实际输出、日志证据、是否通过和回归结果；通过后固化为 V7.0 验收基线。

# 9. 既定开发原则

## 9.1 先本地，后公网

基础链路未稳定时不直接部署云服务器。先在本机/局域网得到可复现的闭环。

## 9.2 先固定值，后模拟数据，再真实数据

固定前端坐标 → FastAPI固定坐标 → MySQL模拟坐标 → Swagger POST → ESP32固定坐标自动POST → L80-R真实GPS。

## 9.3 先读取链，后写入链

已先完成 MySQL→FastAPI→JavaScript→高德；现在才进入 POST→MySQL。

## 9.4 每次只增加一个主要变量

地图、FastAPI、MySQL、POST、真实GPS按层增加；出错时能快速定位责任层。

## 9.5 先单模块，后系统整合

GPS、SOS、跌倒、语音、电量、摄像头均先独立验证，再接接口、数据库和前端。

## 9.6 先HTTP，后WebSocket

第一版 POST 上传 + GET 查询 + HTTP轮询；基础系统稳定后再评估服务器主动推送。

## 9.7 FastAPI统一控制数据访问

设备和网页均不直接连接MySQL；后端是数据、权限和业务逻辑统一入口。

## 9.8 每阶段必须有明确验收

不以“看起来能跑”作为完成标准；必须定义输入、输出、成功现象和故障边界。

## 9.9 页面交互语义优先于视觉装饰

四色Marker的业务含义固定；同坐标时不通过改色合并语义；视觉仅做错位和标签处理。

## 9.10 业务时间与服务器时间分离

历史定位以gps_time为准；服务器写入timestamp用于日志和排错。

## 9.11 V7.0 已确认创新点与优化价值

- 【已确定 / 已实施】1）分层式设备—FastAPI—MySQL—Web 架构：设备与浏览器均不直接访问 MySQL，由 FastAPI 统一承担数据接收、校验和查询，为后续鉴权、设备绑定、告警扩展保留统一入口。
- 【已确定 / 已实施】2）基于 Haversine 的 50 米轨迹抽稀：查询轨迹后按相邻保留点的球面距离进行抽稀，第一个点和最后一个点强制保留，降低高频 GPS 数据对地图绘制的压力。当前尚未完成大规模连续数据的效果验证。
- 【已确定 / 已实施】3）5 km 大跨度地图重定位：正常小范围移动只移动 Marker，跨区域有效定位达到阈值时重新设置地图中心，避免老人正常步行时地图持续晃动。
- 【已确定 / 已实施】4）时间容差定位查询：不要求数据库存在查询时刻的精确秒值，而是在前后5分钟窗口中寻找最近定位，并在前端用信息窗解释实际命中时间与查询时间的差异。
- 【已确定 / 部分实施】5）多模式地图交互：实时定位、今日轨迹、历史轨迹三类模式职责不同；当前模式切换已可运行，但历史收回和后台轮询仍需优化。
- 【未实施 / 有如下优化方法】6）数据驱动的软件验证：推荐用 Python 自动模拟 GPS 替代逐条 Swagger 手工输入，生成连续路线、异常跳点和不同密度数据，形成可重复测试基线。

WebSocket、多设备、复杂鉴权、真实告警、云部署等均不因为“可优化”就提前进入当前主线。先完成 HTTP 软件闭环、异常测试和真实 GPS 接入，再依据实际性能和安全需求评估是否升级。

# 附录 F：GPS 轨迹抽稀关键代码片段

- 【已实施 / 已验证】实际规则为距离阈值50米，而不是5秒或50秒。

```python
def simplify_track(locations, distance_threshold=50):
    if len(locations) <= 2:
        return locations

    result = [locations[0]]
    last_point = locations[0]

    for point in locations[1:]:
        distance = calculate_distance(
            last_point["longitude"], last_point["latitude"],
            point["longitude"], point["latitude"]
        )
        if distance >= distance_threshold:
            result.append(point)
            last_point = point

    # 最后一个点强制保留
    if result[-1]["id"] != locations[-1]["id"]:
        result.append(locations[-1])

    return result
```

计算距离使用 Haversine 公式，作用是把高频 GPS 点压缩到适合地图展示的密度。当前数据规模只有几十条、多日期分布，尚未完成大规模性能验证。
