### 2.2 UART 实物接线（已确认）

已通过实际 NMEA A/B 测试确认的接线结论：

| GPS 小板端 | ESP32 端 | 当前结论 |
| --- | --- | --- |
| RX（小板丝印） | GPIO14 | 已通过实际 NMEA A/B 测试确认：本项目中作为 **GPS 数据输出**接入 ESP32 RX |
| TX（小板丝印） | GPIO13 | 当前代码定义为 GPS_TX；如果 ESP32 不需要向 GPS 发送命令，物理上可暂不接 |

> 注意：该成品小板的丝印与常规模块 TXD（输出）/RXD（输入）方向相反，一律以本实测结论为准，不再按丝印字面推断（GATE-02 通过）。

## 4. 项目核心概述

### 4.1 项目目标

本项目拟开发一套以具备联网能力的老人便携式监护设备为硬件载体，以 GPS 连续定位为第一核心链路，并在 GPS 主链稳定后逐步集成 SOS、跌倒检测、语音对讲、电量监测、摄像头抓拍、设备绑定、多用户鉴权、电子围栏和安全告警等功能的老人户外安全监护系统；监护端通过 Web 页面查看老人当前所在位置、当天轨迹、历史轨迹和设备状态。

### 4.2 GPS 模块的定位与边界

GPS 模块是本项目的第一核心链路，已经从"固定数据能够显示"推进到"设备自动上传、数据库连续保存、网页自动刷新、当天轨迹默认显示、历史日期和具体时间可查询"的完整数据闭环，并完成独立供电、实物接线与定位质量验收。后续跌倒、电量、摄像头、SOS 等模块复用同一套"设备上传 → FastAPI → MySQL → 前端读取"的分层框架（见附篇 B）。

### 4.3 GPS 双向数据链

**写入链（设备 → 数据库）**：

```text
GPS 卫星 / 定位源
        ↓
L80-R GPS 定位模块（WGS84 + GPS UTC 时间）
        ↓ UART 9600 / GPIO14
ESP32 主控（GPS_MONITOR 手机诊断热点 + 自动上传）
        ↓ WiFi / HTTP POST /location
FastAPI 数据校验（UTC → 北京时间）
        ↓
MySQL locations（gps_time + received_at）
```

**读取链（数据库 → 监护端）**：

```text
Web 浏览器
        ↓ JavaScript fetch（同源相对路径，2 s 轮询）
FastAPI
        ↓ MySQL 查询
JSON（WGS84 原始坐标 + gps_time 北京时间）
        ↓ 前端统一转 GCJ-02
高德地图
        ↓
当前位置 Marker + 当天/历史 Polyline + 指定时刻查询 Marker
```

## 5. 系统架构

### 5.1 总体架构与分层职责

系统采用"设备端 — FastAPI 后端 — MySQL 数据库 — Web 前端 — 高德地图可视化"的分层架构。

| 层级 | 职责 | 状态 |
| --- | --- | --- |
| 设备端（L80-R + ESP32） | GNSS 采集、解析、组织数据、联网并 HTTP 上传 | 【已验证】 |
| FastAPI 后端 | 统一 API；接收设备数据；参数校验；时间转换；业务逻辑；读写 MySQL；后续鉴权/告警 | 【已验证】 |
| MySQL | 持久化定位及后续用户/设备/告警数据 | 【已验证】 |
| Web 前端 | fetch 调用 FastAPI；维护页面状态；管理 Marker/Polyline/查询 | 【已验证】 |
| 高德地图 JS API | 底图、Marker、Polyline、视野管理、后续轨迹回放 | 【已验证】 |

浏览器和 ESP32 均不直接访问 MySQL；时间转换、校验、查询和后续鉴权/告警规则集中在 FastAPI。

### 5.2 网络传输方案：HTTP 优先

第一版统一使用 HTTP：设备上传用 POST，网页读取用 GET，实时位置用定时轮询。当前 HTTP POST/GET + 2 s 轮询已稳定工作，WebSocket 只有出现真实的主动推送/性能需求后才评估（见附篇 A.7），不以技术潮流驱动替换。

## 6. 已确认的核心技术方案

### 6.1 硬件与 UART 基线

| 模块 | 型号 | 说明 |
| --- | --- | --- |
| 主控 | ESP32-WROVER-DEV | 已验证硬件 |
| GNSS | Quectel L80-R | 已验证硬件 |
| 串口 | HardwareSerial(2)，9600 baud | GPS_RX=14 / GPS_TX=13，按第 2.2 节实测接线 |
| 网络 | 手机热点 WiFi（本地验证） | 4G 迁移见附篇 B |
| 诊断热点 | GPS_MONITOR（192.168.4.1） | 手机免串口查看 UART/搜星/Fix/上传状态，与上传链路相互独立 |

### 6.2 NMEA 解析与有效 Fix 规则

固件使用 TinyGPSPlus 持续解析 NMEA；只有 location 真正更新且 location/date/time 全部有效时，才更新 latestFix 快照。GPS 丢星或串口停止后，缓存中的旧坐标不会被当作新定位反复上传。

固件上传判断：每 5 s 检查一次是否存在"新的、有效的、新鲜的"Fix（新鲜度 10 s）；HTTP 2xx 才记录为上传成功；GPS 时间不晚于上次成功上传时间则跳过（防重复）。开机 10 s 后若串口几乎没有字符，输出警告提示检查 RX/TX、供电和波特率。

### 6.3 设备上传协议

四字段 POST；gps_time 为 GPS 原始 UTC（ISO 8601，带 Z 时区），北京时间转换统一由后端完成（含跨天正确处理）：

```json
{
  "device_id": "elder001",
  "longitude": 116.123456,
  "latitude": 39.123456,
  "gps_time": "2026-08-28T01:55:30Z"
}
```

> ESP32 不做 GCJ-02 转换、不做手工 +8 小时；原始 WGS84 与 UTC 时间原样上传。

### 6.4 时间语义

| 字段 | 含义 | 生成方 |
| --- | --- | --- |
| gps_time | GPS 实际定位时间（北京时间，UTC+8 转换后无时区 DATETIME） | FastAPI 转换后写入 |
| received_at | 服务器收到并写入的时间 | MySQL 自动生成 |

所有业务查询（最新位置、今日/历史轨迹、指定时刻最近点）均按 gps_time 排序与过滤；received_at 用于分析网络延迟、离线补传和排错。旧数据没有真实 GPS 时间，gps_time 保持 NULL，不伪造回填。

### 6.5 后端 API 边界

| 方法 | 路径 | 核心语义 |
| --- | --- | --- |
| GET | `/` | 返回 frontend/index.html（同源托管） |
| GET | `/api/health` | 服务存活 + 北京时间 server_time |
| GET | `/location` | 按 device_id + gps_time DESC 获取最新位置 |
| POST | `/location` | 四字段上传；gps_time 必须带时区；校验 device_id 与经纬度范围 |
| GET | `/locations/today` | 北京时间今天 00:00 至当前；50 m 抽稀 |
| GET | `/locations/history/date` | 指定日期全天；50 m 抽稀 |
| GET | `/locations/history/range` | 自定义时间范围；前端入口见附篇 A.6 |
| GET | `/locations/nearest` | 指定时刻 ±5 min 中按 gps_time 秒差最近 |

后端返回 JSON 中的 longitude/latitude 始终是 WGS84 原始值；错误处理统一返回明确 HTTP 状态码与 detail；数据库写入失败回滚。

### 6.6 数据库数据模型

数据库 `elder_monitor`，主表 `locations`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | 主键，自增 |
| device_id | VARCHAR(50) | 设备标识（默认 elder001，预留多设备） |
| longitude | DOUBLE | 经度（WGS84 原始值） |
| latitude | DOUBLE | 纬度（WGS84 原始值） |
| gps_time | DATETIME | GPS 实际定位时间（北京时间）；旧数据为 NULL |
| received_at | DATETIME | 服务器接收写入时间 |

索引：主键 `id` + `(device_id, received_at)` + `(device_id, gps_time)`。Foreign Key 与 Trigger 当前不使用（业务规则优先放在 FastAPI，避免逻辑隐藏在数据库触发器内）；后续 devices/user_devices 等表建立后再按数据模型评估外键。

### 6.7 前端与坐标边界

- 数据库 / API：永远保存 GPS 原始 **WGS84**；
- 前端：所有进入 AMap Marker / Polyline / setCenter 的坐标统一先转 **GCJ-02**（含实时点、今日/历史轨迹、指定时刻 Marker，避免覆盖物互相错位）；
- 页面文字与信息窗：显示原始 WGS84，便于与 GPS 串口数据核对；
- 前端 API 全部使用同源相对路径（`/location`、`/locations/today`…），本机与局域网访问无需修改代码。

### 6.8 轨迹与时刻查询规则

- 轨迹抽稀：Haversine 计算相邻点球面距离，相邻保留点达到 50 m 才保留；**第一个点和最后一个点强制保留**，避免轨迹首尾丢失；
- 指定时刻查询：后端将查询时间扩展到前后 5 min 窗口，按 `ABS(TIMESTAMPDIFF(SECOND, gps_time, target))` 选最近记录；返回 query_time、gps_time、difference_seconds、longitude、latitude；若两个候选记录与查询时间差完全相同，选择时间更晚的记录；
- 今日轨迹：北京时间今天 00:00 至当前；历史轨迹：按 YYYY-MM-DD 全天。

### 6.9 页面交互与 Marker 语义

**四色 Marker 固定语义**：

| 颜色/对象 | 固定语义 | 重合时处理 |
| --- | --- | --- |
| 绿色 Marker | 当天第一条有效 GPS = 起点 | 不因查询位置重合而改变颜色 |
| 蓝色 Marker | 最新有效 GPS = 当前所在位置 | 与起点/查询位置同坐标时保留语义并视觉轻微错位 |
| 红色 Marker | 历史日期最后一条有效 GPS = 当天终点 | 只有 1 条数据时与绿色起点同坐标但错位显示 |
| 橙色 Marker | 指定时间对应的最近有效 GPS = 查询位置 | 允许与起点/当前/终点同坐标；点击显示实际命中时间 |
| Polyline | 按 gps_time 从早到晚连接当天有效 GPS | 0 或 1 条记录时不强行画线；每 50 m 取一次点 |

**页面模式**：实时定位 / 今日轨迹 / 历史轨迹三种。今日与历史按钮第二次点击均直接返回实时定位并清理覆盖物。实时模式 2 s 轮询；普通位移只更新 Marker，相邻有效定位距离 ≥5 km 时才重新居中地图。

**日期入口**：历史日期统一下拉（昨天、2 天前、…、5 天前、自定义日期）；选择自定义日期后才显示浏览器日历，最大可选日期为昨天。日期按北京时间（UTC+8）计算，与浏览器时区无关。

**无数据 / 单点规则**：

| 场景 | 地图行为 | 提示/说明 |
| --- | --- | --- |
| 今天 0 条有效 GPS | 不显示轨迹、起点、当前位置、终点 | 显示"今天暂无 GPS 定位数据" |
| 历史日期 0 条 | 清除上一条历史轨迹及相关 Marker | 显示"YYYY年M月D日暂无 GPS 定位数据" |
| 今天只有 1 条 | 无 Polyline；绿色起点与深蓝当前位置同坐标并轻微错位 | 两种业务语义都保留 |
| 历史日只有 1 条 | 无 Polyline；绿色起点与红色终点同坐标并轻微错位 | 两种业务语义都保留 |
| 查询时间命中起点/终点/当前 | 橙色查询 Marker 保留并与原 Marker 轻微错位 | 不替换原 Marker 的颜色和语义 |

**时间输入**：`<input type="time">` 兼容浏览器只返回 HH:MM 的情况，发送前自动补成 HH:MM:SS。

### 8.1 阶段 1：固定坐标 → JavaScript → 高德地图

目的：完全排除 Python、FastAPI、MySQL 和真实 GPS 干扰，只验证 Web 页面、高德 Key、安全配置、JavaScript、地图和 Marker。

做法：建立 index.html → 配置高德 JS API Loader 与安全配置 → JavaScript 人工设置固定经纬度 → AMap.Map 创建地图 → AMap.Marker 显示老人位置 → 自定义醒目蓝色定位针（HTML/CSS content）。

验收：高德底图正常；地图中心正确；Marker 明显且可与高德自身 POI 区分。

### 8.2 阶段 2：FastAPI 固定坐标 → HTTP → JavaScript → 高德地图

目的：只增加 FastAPI 一层，把经纬度从前端固定值搬到后端固定 JSON，地图逻辑不变。

做法：后端返回固定 JSON；前端 fetch `GET /location` 读取后创建 Marker。因当时 5500 与 8000 跨端口，main.py 配置 CORS 允许 5500 来源。

验收：浏览器直接访问 /location 能看到 JSON；前端使用 FastAPI 返回坐标；后端日志出现 GET /location 200。

### 8.3 阶段 3：MySQL → FastAPI → Web 读取链

**3.1 建库建表**：创建业务数据库 `elder_monitor`（utf8mb4）与 `locations` 表（id、device_id、longitude、latitude、timestamp——当时无 gps_time，timestamp 由 MySQL 自动生成）。注意 CREATE TABLE 重复执行会报 Error 1050；INSERT 重复执行会真实增加数据行。

**3.2 模拟数据与排序验证**：先人工 INSERT 固定坐标（如 `('elder001', 116.397428, 39.90923)`），扩展到至少 5 条，用 `ORDER BY id DESC LIMIT 1` 验证"最新记录"查询。ORDER BY 只改变查询结果输出顺序，不改变物理记录。

**3.3 EXPLAIN 索引验证**：对 `ORDER BY id DESC LIMIT 1` 执行 EXPLAIN，确认 type=index、key=PRIMARY、rows=1、Extra=Backward index scan，说明查询沿 PRIMARY 反向扫描即可快速取得一条记录。这建立了后续索引设计思路：真实历史轨迹按 device_id + gps_time 查询（当前表已有对应联合索引）。

**3.4 Python → MySQL 独立验证**：安装 mysql-connector-python，用独立 test_mysql.py 先验证连接、再验证 cursor/execute/fetchone，把问题明确定位到数据库连接层。

**3.5 FastAPI → MySQL**：`GET /location` 从"返回固定坐标"改为"查询 locations 最新记录"。前端 fetch URL 不变——验证了 API 层对前端的数据源屏蔽作用。

**3.6 A/B 坐标端到端验收**：保持 main.py 和 index.html 完全不变，只在 MySQL 插入第 6 条明显不同的坐标 B，刷新页面后 Marker 移动到 B。结论：MySQL → FastAPI → HTTP GET → JavaScript → 高德地图的读取链完整成立。

> 历史说明：阶段 3 建表时还没有 gps_time；后续阶段 6 落地双时间模型时，旧数据保持 gps_time=NULL（不伪造回填），timestamp 语义由 received_at 取代。

### 8.4 阶段 4：POST /location 写入链

在读取链基础上增加写入接口：Swagger 手动 POST → FastAPI 校验（device_id 非空、经纬度范围）→ INSERT locations → MySQL 新增记录 → GET /location 读取 → 前端 2 s 轮询显示。验收：Swagger 返回上传成功；MySQL 增加记录；前端下一轮轮询显示新坐标。标准写入入口随后从"仅 Swagger"扩展到"ESP32 自动 POST"，Swagger 与 Workbench 保留为调试与对照工具。

### 8.5 阶段 5：ESP32 自动上传 + 真实 L80-R 接入

ESP32-WROVER-DEV + Quectel L80-R 实机联调：TinyGPSPlus 解析真实 NMEA（卫星数、经纬度、海拔、UTC 时间），ESP32 通过手机热点 WiFi 自动 POST /location，连续写入 MySQL 并收到 HTTP 200。

### 8.6 阶段 6：gps_time 双时间模型落地

- 固件：GPS 日期/时间组合成 ISO 8601 UTC（如 `2026-08-28T01:55:30Z`），随四字段 JSON 上传；构建 gpsTimeKey 用于时间递增判断；
- 后端：带时区校验（必须含时区，否则 400），完整时区转换（跨天正确），写库前去掉 tzinfo；
- 数据库：gps_time（业务定位时间）+ received_at（服务器接收时间）双字段；所有轨迹与 nearest 查询切到 gps_time；
- 验收：03:27:17Z → 11:27:17 北京时间写入验证通过。

### 8.7 阶段 7：最新位置按 gps_time + 乱序测试

`GET /location` 从"全表 id DESC"改为"WHERE device_id + ORDER BY gps_time DESC, id DESC"。即使网络延迟导致较旧 GPS 点晚到服务器，也不会覆盖真正较新的位置。乱序测试通过。

### 8.8 阶段 8：FastAPI 同源托管 Web

FastAPI 通过 FileResponse/StaticFiles 托管 frontend/index.html，浏览器统一访问 8000 端口，不再依赖 5500 静态服务器；健康检查单独放到 `/api/health`；前端 API 全部改为相对路径，本机/局域网访问无需改代码。

### 8.9 阶段 9：WGS84 → GCJ-02 展示转换

前端实现标准 WGS84→GCJ-02 转换（中国范围外原样返回），实时 Marker、今日/历史轨迹、指定时刻 Marker、地图居中全部统一先转换后绘制；数据库/API/页面文字继续保留 WGS84 原始值。地图偏移问题解决。

### 8.10 阶段 10：WiFi 自动重连 + 旧 Fix 防重复

固件运行中断线后每 10 s 主动重连（不阻塞 GPS 串口解析）；HTTP 设置 5 s 超时；只有 2xx 才记录"已成功上传"；Fix 新鲜度 10 s + gpsTimeKey 递增判断，杜绝旧坐标重复写入。

### 8.11 阶段 11：增强版固件（GPS_MONITOR 手机诊断热点）

在完整上传固件上增加 WebServer 与 GPS_MONITOR AP（WIFI_AP_STA 双模式）：STA 端连接主热点负责 FastAPI 上传，AP 端建立诊断热点供手机免 USB 串口查看 UART 字符、搜星、Fix、WiFi 与上传状态。两个 Wi-Fi 功能相互独立：不连接 GPS_MONITOR 不影响自动上传；主热点不可用时手机仍可看本地状态。

### 8.12 阶段 12：独立供电 + UART 接线 + 定位质量（2026-10）

见第 2 章实测更新记录：充电宝全链路成功；小板丝印 RX→GPIO14 实测接线确认；定位质量初步验收通过。

### 9.2 细节问题与解答（开发过程积累）

| 问题/现象 | 确认原因 | 最终解决办法/固化结论 |
| --- | --- | --- |
| 地图底图有 POI，老人位置不明显 | 高德自身 POI 与定位标记混淆 | 使用自定义 HTML/CSS content 的醒目蓝色定位针 |
| 直接运行 main.py 后终端结束 | 只定义 app 不等于启动服务 | 统一使用 `uvicorn main:app` |
| 跨端口访问失败/涉及跨域 | 不同端口属于不同 Origin | 正式方案为同源托管；调试 CORS 后续清理 |
| 直接双击 HTML 打开页面异常 | file:/// 不是标准 HTTP Origin | 必须通过 HTTP 服务访问 |
| Workbench 左侧未立即看到新对象 | 对象树需要刷新 | 以 Action Output 为执行结果依据 |
| 重复 CREATE TABLE 报 Error 1050 | 表第一次已创建成功 | 不删除成功表，只停止重复执行 |
| 重复 INSERT 会多出记录 | INSERT 是真实数据写入 | 每次 INSERT 明确目的并核对 rows affected/id |
| ORDER BY id DESC 能否代表最新 GPS | 模拟阶段 id 与插入顺序一致；真实设备可能乱序 | 统一引入 gps_time 并切换业务时间 |
| MySQL 程序目录与数据目录混淆 | Server 程序与数据文件不是一回事 | 数据由 MySQL 管理，禁止手工修改数据文件 |
| Workbench 是否必须一直开 | Workbench 只是客户端 | 运行链只需 MySQL Server + FastAPI + 浏览器 |
| GPS 字符数固定不动、距最后字符时间增大 | UART 数据流中断（接触/线序/供电） | 优先查杜邦线接触、VCC/GND、GPIO14，不要误判为"搜不到星" |
| 充电宝供电异常 vs 电脑 USB 正常 | 可能是移动设备改变接触状态（实测结论之一） | 先确认连接可靠性，再怀疑电源问题 |

## 13. 既定开发原则与创新点

### 13.1 开发原则

1. **先本地，后公网**：先在本机/局域网得到可重复闭环，独立供电和长时运行达到门槛后再迁移 4G/公网；
2. **先固定值，后模拟数据，再真实数据**：Python 模拟器转型为回归/故障注入工具，不再是真实硬件前置；
3. **先读取链，后写入链**：先证明 MySQL→FastAPI→Web 读取链，再实现 POST→MySQL 写入链；
4. **每次只增加一个主要变量**：地图、FastAPI、MySQL、POST、真实 GNSS、gps_time、坐标转换、网络恢复按层增加；
5. **先单模块，后系统整合**：GPS 主链稳定前不并行堆叠 SOS、IMU、语音、摄像头；
6. **第一版优先 HTTP，确有必要再评估 WebSocket**；
7. **FastAPI 统一承担后端业务和数据库访问**；
8. **每个阶段必须有明确验收标准**：保留输入、预期、实际、证据和是否通过；
9. **当前事实优先于旧路线**：已完成事项从"下一步"移出，已失败事项不隐藏；
10. **原始数据与展示数据分离**：WGS84 与 GCJ-02、gps_time 与 received_at 同理，原始事实不因界面便利被改写。

### 13.2 已确认的创新点与优化价值

1. **分层式设备—FastAPI—MySQL—Web 架构**：设备与浏览器均不直接访问 MySQL，由 FastAPI 统一承担数据接收、校验和查询，为鉴权、设备绑定、告警扩展保留统一入口；
2. **基于 Haversine 的 50 m 轨迹抽稀**：相邻保留点球面距离达阈值才保留，首末点强制保留，降低高频 GPS 数据对地图绘制的压力；
3. **5 km 大跨度地图重定位**：正常小范围移动只更新 Marker，跨区域有效定位达阈值才重新居中，避免地图持续晃动；
4. **时间容差定位查询**：±5 min 窗口内找最近定位，信息窗解释实际命中时间与查询时间的差异；
5. **多模式地图交互**：实时定位、今日轨迹、历史轨迹三类模式职责不同，二次点击直接返回实时并清理覆盖物；
6. **WGS84/GCJ-02 工程分层**：数据库永远保存原始坐标，展示层统一转换，避免覆盖物互相错位与重复转换；
7. **gps_time/received_at 双时间模型**：业务时间与服务器时间分离，为断网补传、延迟/乱序上传提供真实时序依据。

### 13.3 补充原则

- 设备数据输入必须可追溯（采集时间与接收时间分开保存）；
- 安全判断优先服务端统一规则（告警、离线、围栏由 FastAPI/后台规则层产生，网页只显示）；
- 用户首页以"现在是否安全"为中心（后续在大系统阶段实现）；
- 保持当前主线不做过早技术升级（WebSocket、复杂鉴权、云部署等按实际需求评估）。

```sql
CREATE TABLE `locations` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `device_id` varchar(50) NOT NULL,
  `longitude` double NOT NULL,
  `latitude` double NOT NULL,
  `gps_time` datetime DEFAULT NULL,

  PRIMARY KEY (`id`),
  KEY `idx_locations_device_received_at` (`device_id`,`received_at`),

) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

```sql
WHERE device_id='elder001'
ORDER BY gps_time DESC, id DESC

SELECT * FROM locations
WHERE device_id='elder001'

  AND gps_time <= '2026-08-29 23:59:59'
```
